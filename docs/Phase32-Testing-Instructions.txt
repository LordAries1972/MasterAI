Prerequisites — two compatible models
select_speculative_draft_candidate() requires a draft model that's a different id, same architecture, same format, same backend, smaller size, and both models 
must have license_accepted: true and be in ready state (digest-verified). E.g. a 1B-3B "draft" and a 7B-8B "target" of the same family (both GGUF, both llama.cpp-compatible architecture string).

Step-by-step (as an administrator)
Confirm both models are ready — GET /api/v1/models and check state.

Record advanced-optimization evidence for speculative_decoding — POST /api/v1/performance/advanced-optimizations:


{"feature":"speculative_decoding","action":"record-evidence","evidence":{
  "baselineDescription":"single-model generation, same prompt suite",
  "changedSetting":"dual-model speculative decoding enabled",
  "hostHash":"<any stable string>","modelSha256":"<target model sha256>",
  "backendHash":"<llama-server exe sha256>","timeToFirstTokenMs":0,
  "promptThroughputTokensPerSecond":0,"generationThroughputTokensPerSecond":0,
  "peakResidentMemoryBytes":1,"qualityNotes":"manual smoke test",
  "powerThermalNotes":"n/a","regressionDetected":false,"fallbackVerified":true}}
regressionDetected must be false and fallbackVerified must be true, or admit will refuse.

Admit the feature — POST /api/v1/performance/advanced-optimizations with {"feature":"speculative_decoding","action":"admit"}.

Submit a qualifying per-pair acceptance rate — POST /api/v1/performance/speculative-pairs:


{"targetModelSha256":"<target sha256>","draftModelSha256":"<draft sha256>","acceptanceRate":0.75}
Must be ≥ 0.6 (the default minimum_acceptance_rate) or decide_speculative_decoding_for_request() rejects it. This is the number you'd normally get from a real 
measured run — for a first smoke test you can submit an honest placeholder like this and lower it later once you have real numbers.

Load the target model and send a chat request with chat_max_reply_tokens configured ≥ 64 tokens (the default minimum_tokens_to_bother).

Verify the dual-model launch actually happened — this is the part that needs real confirmation, not just "no error":

Check the runner log: <runtime_root>/logs/runner-<target-model-id>.log — llama-server logs its own startup flags, so you should see --model-draft <path> in there.
Or check the live process command line in PowerShell:

Get-CimInstance Win32_Process -Filter "name='llama-server.exe'" | Select-Object CommandLine
Confirm --model-draft appears.
Task Manager should also show more resident memory than a single-model load (both models mapped concurrently) — a rough sanity check that two models are actually loaded.
If none of that shows --model-draft, the most likely reason is select_speculative_draft_candidate() found no compatible draft — double check both manifests' 
architecture/format/backend strings match exactly, and that a model smaller than the target is actually registered and ready.

That's the wiring check. Actually measuring whether it speeds anything up (the still-open exit criterion) means comparing generation throughput with the 
feature admitted vs. disabled on the same prompt suite — that's the real-hardware benchmark that's still outstanding.
